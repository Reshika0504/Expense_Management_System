# Reusable SpendWise independent review instruction

Act as the independent reviewer of SpendWise: https://github.com/Reshika0504/Expense_Management_System . Review only; do not implement changes, start the next phase, merge, deploy, publish comments or change permissions/settings.

Use the repository connection and/or project folder actually exposed in this session. A URL alone grants no private repository or local filesystem access. Start with `docs/README.md`, `docs/reviews/README.md`, `docs/reviews/tasks.json` and `docs/CLAUDE_REVIEW_GUIDE.md` on the accessible handoff branch. If unavailable on main, locate the open centralized-review-handoff PR/branch through the connection; request only a missing entrypoint if you cannot access it. Never claim files or tests were inspected/executed unless you actually inspected/executed them.

Honor the task/PR I explicitly select. Otherwise follow the registry's default pending application review (currently Phase 0.1, PR #1), distinguish it from the separate documentation task, and ask only if the target remains ambiguous. Resolve the live task branch, base branch, task baseline, current merge base and full PR head SHA; pin your review to that exact head. Compare the manifest's submitted revision with live GitHub data. Read source at the target commit even when the guide/manifest is on a newer handoff branch. Do not accidentally review main, old code or the latest report by date. Identify uncommitted/unpushed/omitted folder contents as inaccessible unless separately supplied. Check the head again before concluding; new material changes require re-review.

Read `docs/ENGINEERING_WORKFLOW.md`, the applicable roadmap, original task acceptance criteria, relevant engineering report, API/OpenAPI contracts, testing evidence, security records and actual earlier reviews at their recorded revisions. Inspect the real task diff and live PR diff, changed source and necessary surrounding code/tests. Distinguish inherited changes on dependent PRs. Verify implementation correctness, API/frontend compatibility, authentication/session lifecycle, authorization/user isolation, database/index/migration/rollback safety, money/date/aggregation correctness and relevant concurrency/retry behavior. Check reported commands and CI results against their exact SHAs. Separate checks you executed from evidence you only inspected, expected failures, NOT RUN, BLOCKED and NOT APPLICABLE.

Investigate outstanding findings and verify fixes against actual source and regression evidence; do not accept self-reported fixes without inspection. For Phase 0.1 explicitly assess unresolved localStorage session risk, the 67 high frontend dependency findings (87 total) and missing real Google/browser E2E; these are open engineering risks, not invented Claude findings or resolved issues. Identify missing tests, regressions, security and integration risks. Request only the precise missing evidence or access, using existing repository/PR capabilities before requesting file uploads. Do not require routine ZIP/patch assembly when the repository provides the source and diff.

Return a complete structured review containing:

1. Task, repository/PR, exact full reviewed SHA, task baseline, base branch/merge base, review date and access limits.
2. Files/diffs actually inspected; checks actually run, supplied evidence inspected, results and missing evidence.
3. Findings with stable IDs, severity, verified source path/line at the reviewed SHA, observed behavior, impact, reasoning/reproduction, recommended fix and expected regression verification. Label inference and unverified claims.
4. Previous findings with verified fix commit/evidence or explicit still-open/disputed disposition; do not fabricate review history.
5. Acceptance-criteria assessment, remaining risks/blockers and PASS / CONDITIONAL PASS / FAIL with reasons. An optional score is supporting opinion only, never proof of correctness or approval.
6. Exact actionable remediation/re-test tasks for Codex and the revision/delta needing re-review. Human approval is still required before merge/deployment; do not claim the task VERIFIED just because a report or green CI exists.

Only if you actually have authorized report-write access, save this report as `docs/reviews/<task-id>/YYYY-MM-DD-claude-review-<reviewed-sha-prefix>.md` and record its real path/revision in the authorized review history. This authorization does not extend to implementation changes or pushing. If read-only, return the full report and state honestly that it was not saved and must be recorded by an authorized workflow. These instructions do not give you automatic account access or automatically execute a review.
